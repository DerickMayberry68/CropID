# CropID Role And Permission Model

This document defines the initial role and permission boundaries for the CropID platform.

The goal is to prevent the farmer app, farmer web app, and ag spraying service portal from drifting into unclear or unsafe access patterns as the platform expands.

## Purpose

CropID is evolving into a multi-surface platform with distinct user groups:

- farmers
- ag spraying service operators
- internal administrators

Each group should have access only to the data and actions required for its job.

This document defines:

- platform roles
- ownership boundaries
- shared workflow objects
- recommended access rules
- future implementation considerations

## Core Principles

Permission design should follow these rules:

- least privilege by default
- farmer data remains farmer-owned unless explicitly shared
- service portal access is operational, not open-ended
- cross-party workflows should use explicit request objects, not implicit access
- admin access should be controlled and auditable

## Primary Roles

### 1. Farmer

A farmer is the primary end user of the current mobile app and future farmer web app.

Core responsibilities:

- manage fields
- manage crop and chemical context
- create spray plans
- review neighbor-risk alerts
- contact spraying services
- review their own operational history

Access expectations:

- can read and write their own profile
- can read and write their own fields
- can read and write their own spray plans
- can read alerts addressed to them
- can discover available spraying services
- can create service requests

A farmer should not:

- view private operational data of other farmers
- view service internal schedules
- modify service-side job statuses

### 2. Service Operator

A service operator is a user within the ag spraying service portal.

This role represents the commercial spraying business side of the platform.

Core responsibilities:

- receive requests from farmers
- review job opportunities
- accept, reject, or schedule jobs
- manage service territory, equipment, crews, and customer workflow

Access expectations:

- can read and update their own service organization profile
- can read service requests assigned to or routed to their organization
- can manage jobs belonging to their organization
- can view farmer-provided details that are explicitly shared in a request
- can update job status for accepted work

A service operator should not:

- browse arbitrary farmer records
- access unrelated farmer fields or plans
- access other spraying services' jobs, customers, or schedules

### 3. Service Manager

This is a higher-privilege role inside a spraying-service organization.

Core responsibilities:

- manage organization-wide settings
- manage staff and dispatch workflows
- oversee equipment and territory
- access reporting for their organization

Access expectations:

- all service operator permissions
- can manage internal service users
- can manage organization settings
- can access organization-wide reports and queues

### 4. Platform Admin

This is an internal CropID administrative role.

Core responsibilities:

- support and troubleshoot the platform
- review abuse or operational issues
- manage system-level service approvals or directory quality
- inspect platform health and data integrity

Access expectations:

- elevated read access where operationally necessary
- tightly controlled write access
- audit logging should exist for sensitive admin actions

Platform admins should not be treated as ordinary product users.

## Product Surface To Role Mapping

| Product Surface | Primary Roles |
|---|---|
| Farmer Mobile App | Farmer |
| Farmer Web App | Farmer |
| Ag Spraying Service Portal | Service Operator, Service Manager |
| Internal Admin Tools | Platform Admin |

## Core Data Objects And Ownership

### Profile

Ownership:

- farmer owns farmer profile
- service organization owns service profile
- internal admins do not own user profiles, but may audit/support them

Rules:

- users can edit their own profile
- users cannot edit another organization or user profile unless they are an authorized manager/admin

### Fields

Ownership:

- farmer-owned

Rules:

- only the owning farmer can create, update, or delete their fields
- neighboring farmers should only see what the visibility model allows
- service operators should not automatically gain direct field access

### Spray Plans

Ownership:

- farmer-owned

Rules:

- only the owning farmer can create or modify a spray plan
- service operators should not automatically see all farmer spray plans
- a spray plan should only be exposed to a service through an explicit service-request flow

### Danger Notifications

Ownership:

- generated by platform logic
- visible only to the intended recipient farmer and authorized system logic

Rules:

- recipient farmer can read their notifications
- sender should not gain visibility into recipient inbox state
- service operators should not access farmer danger notifications by default

### Crop Duster Service Directory Entry

Ownership:

- service organization-owned

Rules:

- farmers can browse public service directory data
- service organizations can edit only their own listing
- admins may moderate or approve listings

### Service Request

This should become a first-class object if the service portal is built.

Ownership:

- created by farmer
- assigned or routed to a service organization

Rules:

- farmer can create and review their own requests
- receiving service can review and act on assigned requests
- requests should act as the permission bridge between farmer workflow and service workflow

This is important:

The platform should not grant a service broad access to farmer data just because a farmer contacted them once. Access should flow through the request and job records.

### Job / Scheduled Service Work

Ownership:

- service-organization-owned after acceptance

Rules:

- service organization can manage the operational job lifecycle
- farmer can see only the farmer-facing status and details relevant to their request
- internal notes should remain service-private unless explicitly shared

## Visibility Model

### Farmer Visibility

Farmer data should be split into:

- private
- shared-by-workflow
- public/service-directory-visible

Examples:

- profile phone/email: private unless explicitly used in a workflow
- fields: private except for allowed neighboring visibility
- spray plans: private unless turned into a service request
- service directory listing: public

### Service Visibility

Service organizations should have:

- public directory presence
- private internal operational data
- request-scoped visibility into farmer-shared data

## Recommended Permission Rules By Object

| Object | Farmer | Service Operator | Service Manager | Platform Admin |
|---|---|---|---|---|
| Own profile | Read/Write | Read/Write own org user | Read/Write org users/settings | Controlled support access |
| Fields | Read/Write own | No | No | Controlled support access |
| Spray plans | Read/Write own | No direct access | No direct access | Controlled support access |
| Danger notifications | Read own | No | No | Controlled support access |
| Service directory | Read | Read own listing | Read/Write own listing | Moderate/manage |
| Service requests | Create/Read own | Read/act on assigned | Read/act/report on org assigned | Controlled oversight |
| Jobs | Read farmer-facing statuses only | Read/Write assigned | Read/Write org-wide | Controlled oversight |
| Internal service operations | No | Assigned scope | Org-wide | Controlled oversight |

## Workflow Permission Boundaries

### Farmer Creates Spray Plan

- farmer owns spray plan
- plan remains private to farmer
- neighboring farmers may receive notifications generated from platform logic
- no service gets direct access yet

### Farmer Requests Spraying Service

- request becomes the permission bridge
- only the targeted or assigned service sees the shared request data
- service sees only the data needed to quote, schedule, or perform the job

Suggested shared request fields:

- farmer name or organization
- field name
- field location summary
- requested service details
- chemicals or treatment requirements if intentionally shared
- risk or timing context needed to perform the work

### Service Accepts Job

- accepted job becomes a service-owned operational record
- farmer sees customer-facing status updates
- service keeps internal dispatch notes private

## Admin Considerations

Admins should be separated from standard product roles.

Recommended admin capabilities:

- approve or moderate service listings
- inspect broken workflows
- view audit trails
- resolve support issues
- review abuse/safety incidents

Recommended admin safeguards:

- audit logging
- explicit admin roles
- limited write operations
- clear separation from customer accounts

## Recommended Backend Direction

To support this model cleanly, the backend should move toward explicit role-aware entities instead of overloading current farmer-only entities.

Likely future additions:

- service_organizations
- service_users
- service_requests
- jobs
- job_status_history
- audit_logs
- role_assignments

## Current Recommendation

For now:

- keep current farmer-owned entities locked to the authenticated farmer
- treat service portal planning as requiring new request/job entities
- do not expose spray plans directly to service users
- use explicit workflow objects to share data across roles

## Open Questions

These should be resolved before service portal implementation begins:

1. Can a farmer send a request to one service only, or to multiple services?
2. Will service operators have individual user accounts or only one account per organization?
3. Does the platform need dispatcher, technician, and manager roles separately?
4. What farmer data is allowed to remain visible after a job is completed?
5. What audit/reporting requirements apply to admin or compliance actions?
